# 2026-11-01 架构与质量审视

## 判断

认可全身视频动画迁到现有 Electron 播放能力、静态几何规范、真实返程素材、原生循环等方向。当前实现应称为“渲染路径迁移、引擎补丁和素材管线扩充”，尚不能认定为已经完成、可持续交付的高质量架构重构。

旧 WPF 架构有明确的负载来源：PowerShell UI 定时器调度、PNG 图集解码及大位图管理。它已有异步解码、媒体时钟、故障降级和缓存边界等机制，并非天然错误。长视频动作交给 Chromium 媒体管线合理，但重构收益仍需同条件对照测试，不能由技术名称或素材数证明。

本轮只读审查及假视频回调复现，没有修改正式代码、配置、素材或启停应用。结论不包含实机视觉通过。

## 已复现的播放缺陷：旧异步请求可以覆盖新请求

安装文件：`%USERPROFILE%\AppData\Local\Programs\DeepSeekActionPet\node_modules\dsh-pet\runtime\electron-helper\sprite.js`。

- `switchTo` 的 `onReady` 和 `commitSwitch`（约 430、433 行）仅在 pending 存在且代次不同时拒绝提交。
- 新请求已成功提交后 pending 被置空，此时旧的 requestVideoFrameCallback 仍能通过守卫。
- 隔离复现结果：先成功提交 newer，anim=newer/front=1；再触发旧回调，变为 anim=older/front=0。旧视频仍为实际 target，前后台索引与动作状态可能失配。
- 加载超时只清 pending，未使原请求回调失效。另一用例中，超时后的 loadeddata 仍提交 timedout 动作。
- 这是按特定回调顺序确定复现的逻辑缺陷，不代表已经测出实机发生频率；也未据此断言全部由本次重构新引入。
- dispose 未统一管理这些视频加载监听、加载计时器与视频帧回调，生命周期闭环仍不完整。

复现直接提取当前安装的 switchTo 方法，以假视频和受控回调运行，不启动 Electron、不加载文件视频、不联网。代码与结果：

需要的架构能力是：每次切换拥有可取消请求标识；提交时始终验证当前代次及存活状态；失败、超时、替换、销毁走同一个取消出口；过期回调绝不写播放状态。仅增加延时与 if 分支不足以保证此契约。

## 工程结构缺口

1. **正式来源未统一。** 维护源码、安装、部署清单分叉；三条运行路径有不同配置。独立 Electron 外壳共用 DeepSeek 的 node_modules 与 Electron，属于共享运行时，不是可独立更新和回退的隔离产品。
2. **行为与渲染耦合。** PetSprite 同时处理视频切换、随机行为、工作恢复、物理、点击、菜单、窗口几何和聊天。闲置、拖拽、抛掷、移动、待加载、一次性播放等状态通过分散字段和回调相互约束，缺少集中表达优先级和合法转换的调度层。
3. **角色规则写入通用引擎。** 龙娘命中区域、中文动作名、`pet.extra`/是否有 landing 与“是否团子”绑定。素材是否存在与角色能否形变是两个概念，应由明确的角色能力/动作语义配置表达；不能长期靠资源存在性推断。
4. **构建和发布混在一起。** normalize_step03.py 直接覆盖生产目录；generate_phase3_ecosystem.py 直接改生产配置，且保留重新加入工作/额度随机池的逻辑。多份历史补丁可重复写安装文件，缺少唯一构建入口、暂存验证、原子发布和匹配的回退清单。
5. **制作来源不够确定。** normalize_step03.py 对展扇/提灯会读取已有生产 WebM，根据帧数决定保留再编码。构建产物取决于现场旧文件，不仅取决于母版和配置；干净环境不一定重建同样的完整动作。
6. **离线制作内存没有明确上限。** normalizer 将整段 RGBA 读取并缓存多个动作；视频越多，内存随缓存增长。离线任务可接受较高资源开销，但应记录峰值、界限和失败恢复；它不是可据文档认定的“零开销”管线。

## 质量评价方式需要调整

- 首末帧轮廓 IoU 接近 1，只证明轮廓接近，不证明中间肢体自然、尾巴结构正确、收势没有重影或背景没有闪烁。
- smooth_settle_forward 用最后 18 帧逐步混入静态待机，末帧强制复制待机。它能提高接点指标，但不等同于真实连续收势；应逐动作决定可否采用。
- 两段姿态不同的视频用 180ms 透明淡化，只能改变切换方式，不能补出真实运动。统一高度和脚线有帮助，无法消除姿态不同造成的双影。
- normalize_step03.py 默认以 VP9 CRF 24 输出，未启用 lossless 模式。“无损母版”不能解释为“WebM 成品无损”。是否需要更高质量压制应靠放大对比与存储/解码实测决定，不能盲目改参数。
- idle=75 是掷骰概率，不是待机占总时间的精确比例；长动作、事件和交互都会改变实际观看时间。
- 1.5 秒起步/刹车是配置值，不是脚步与桌面位移同步的证明。要检查步态支撑相位、运动速度与起停时刻。
- 当前 70 项回归覆盖既有维护源码；没有形成针对新视频切换竞争、资源失败、销毁取消和动作链的充分验证。原生 loop 也需要长时间运行采样来验证稳定性与资源占用。

## 面向高质量的收敛路线

不建议现在推倒重来，也不建议继续用动作数量作为进度主指标。

1. 保存可回退基线，确定一个正式全身渲染入口；明确 WPF 半身/额度功能与 Electron 全身的边界、事件适配方式，迁移前保留功能与设置。
2. 将视频播放器、行为调度、物理与窗口宿主、状态适配、资产登记分开。优先抽出易于隔离测试的播放器与调度契约，而不是为文件数量拆类。
3. 先修已复现的请求竞争和超时取消，覆盖连续点按、拖拽转落地、旧请求晚到、缺文件及销毁场景。
4. 制作脚本只产出候选目录和带哈希的清单，检查通过后由单一部署入口发布；完整动作必须从明确母版可重建。
5. 少量代表动作先过视觉门槛：待机、侧身、挥手、长道具、落地、漫游。评估角色一致性、接点、运动中连续性、输入响应和中断恢复，再扩充。
6. 同样大小、素材和桌面环境下记录 WPF/Electron 的 CPU、私有内存、GPU、帧间隔分布、输入到首个实际显示帧的延时、解码重载/失败数；区分冷启动、连续播放、频繁切换和长时间闲置。性能阈值应依据实测和视觉目标制定。

最终标准应是：少量动作也能稳定、自然、可预测地播放；故障可恢复；版本可复现可回退；后续扩充不会破坏这些属性。当前工程已有可保留成果，但尚缺这一层质量保证。

# GPT 娘失焦后鼠标不响应

现场版本 `0.8.4-electron`。用户反馈拖动、按压均无反应，DeepSeek 正常。

## 已取得的实际证据

- 自动操作前保留了原进程，没有先重启。自动操作工具会先激活目标窗口；操作后用户反馈“现在能拖动”。
- 再请用户点击其他应用，然后直接操作 GPT 娘，用户确认“切换窗口后又失效”。这与旧测试只在窗口已激活时成功不同。
- 只读 Win32 探针使用独立进程的 Per-Monitor V2 DPI 感知，避免诊断坐标被 DPI 虚拟化。40 次采样中有 25 次鼠标位于窗口内：Windows 命中目标桌宠、`WM_NCHITTEST=HTCLIENT`、原生穿透标志关闭、程序缓存穿透也关闭，但鼠标按下计数始终停在 21。此时前台是另一个应用，桌宠带 `WS_EX_NOACTIVATE`。
- 因此这次失败发生在激活/系统输入投递阶段，不是已收到按下后又卡在拖动状态。此前测试计数和主动激活后的操作不能替代这一场景的验收。

只读探针源码和有限现场记录保存在 `work/gpt-electron-native-input-20261103-01`，探针没有被装进正式桌宠，也没有修改系统设置。

## 修复候选

`0.8.5-electron` 将主窗口和可点击的文字卡片设为可聚焦，和当前 DeepSeek 交互窗口一致。仍使用 `showInactive()` 显示，不在启动时主动抢焦点；用户实际点击人物或卡片时允许正常激活并接收输入。

同时将窗口就绪、卡片尺寸更新后的置顶状态重新应用到最新设置，避免创建/缩放阶段撤销层级。验证中记录卡片由 480×446 调为 651×607 且原生置顶读数符合要求。隐藏窗口的属性不能在页面就绪前作可靠断言，本轮另以真正的隐藏窗口对比加载前后标志。

修复了验证入口未重置假数据形态的问题：前一轮失败停在半身时，不再影响下一轮全身启动检查。这里只重置隔离 `test-state`，不接触个人数据。

诊断增加真实窗口是否可聚焦、是否已经聚焦，便于今后区分“激活后正常”和“未激活时可直接操作”。验证增加主窗口可激活的契约检查；最终是否修好必须以用户从其他应用直接按压/拖动后的反馈和原生窗口标志为准。

正式安装 150 项回归通过，50 项本地测试通过。正式恢复后只读核查确认 `WS_EX_NOACTIVATE=false`、置顶与显示正常，前台仍为其他应用，未用自动操作工具先激活人物。用户用实际鼠标来回切换后确认“切换后点按、拖动都正常”。这些是本轮最终验收依据。

正式安装和最终验证结果分别见工作目录下 `installed-verification.json`、`finalized.json`、`native-after-start.json`、`user-validation.json`。保留上一版本回退；素材、DeepSeek 和稳定代理不替换。用户在复验期间切换形态的正常修改予以保留，不用安装前备份覆盖。

相关官方 API：[Electron BaseWindow](https://www.electronjs.org/docs/latest/api/base-window)。本轮判断以本机实际对照和 Win32 现场为主，不把一般 API 说明当成已复现的证明。

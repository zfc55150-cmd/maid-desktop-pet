# DeepSeek 桌宠美术流程与 GPT 龙娘复刻方案

研究日期：2026-10-22，北京时间。范围：公开作者资料、制作脚本、本机现有媒体与 GPT 制作记录。此次没有生成新美术、调用付费模型、下载模型、安装或重启桌宠。现有文件中较早的运行验收仅作为历史证据。

**结论：要接近用户认可的 DeepSeek 效果，优先改善母图的视觉层次、连续动画源片与人工级边缘处理，再检查真实播放。更高分辨率、更多帧或更多动作都不能替代这些环节。公开资料足以复现生产流程，但不足以保证逐像素复现原作者结果。**

**一、已经证实的制作流程**

本机 DeepSeek 维护清单记录基线为 dsh-pet 0.3.7。作者 PC2005-cloud 在自己的社区帖子中明确说明动画由豆包生成。这里的“DeepSeek 桌宠”指角色和软件项目，并不代表动画由 DeepSeek 模型生成；从公开流程看，核心动画素材是事先生成的视频，而非实时生成或 Live2D 骨骼动画。[作者原帖](https://github.com/deepseek-ai/deepseek-harness/discussions/2026)

```mermaid
flowchart LR
    A[角色参考图] --> B[逐秒动作设计]
    B --> C[豆包生成绿幕连续视频]
    C --> D[PR手工抠像与遮罩]
    D --> E[统一人物尺度和落脚点]
    E --> F[透明WebM播放变体]
    F --> G[双缓冲播放与动作池]
```

作者的动作规范包括：固定镜头和人物尺度、完整身体与安全边距、人物以同一站姿开始和结束、道具有出现和退出过程。动作写成起势、主要表演、收势等时间段，而不是仅输入“可爱地动起来”。这使不同视频更容易在共同站姿处衔接。[原始动作规范](https://github.com/PC2005-cloud/dsh-pet/blob/main/prompts/桌面宠物%2010%20秒动作提示词.md)

作者 README 明确写明发布动作全部使用 PR 手工抠像路线，自动 HSV 抠像保留为兜底。导入脚本接收带透明通道的 MOV，例如 ProRes 4444 with alpha，再转成透明视频。手工抠像并不等于逐帧手绘原画；它主要处理背景、轮廓、道具和复杂透明边缘。[作者流程说明](https://github.com/PC2005-cloud/dsh-pet#从零生成你自己的宠物完整流程)、[PR 导入脚本](https://github.com/PC2005-cloud/dsh-pet/blob/main/scripts/pr_import_step02.py)

实际归一化代码用首尾站立帧估算人物高度，得到整段共用的缩放与平移；水平中心采用透明前景像素的中位位置，另扫描全片边界。工作画布为 2160×1215，目标站立高度为 900。**这是构图和尺度统一，不是证明原始视频具有 2160 像素的真实细节，也不是每帧把人物拉成一样高。**[归一化代码](https://github.com/PC2005-cloud/dsh-pet/blob/main/scripts/normalize_step03.py)

最后编码脚本的实际参数是 640×360、24fps、VP9 和透明通道。文件开头仍有旧方形尺寸说明，应以实现常量为准。Electron 中用两个视频元素轮换，下一段加载就绪后再切前台，旧段停播。共同站姿解决形体跳变，加载缓冲解决切换等待，两者职责不同。[编码代码](https://github.com/PC2005-cloud/dsh-pet/blob/main/scripts/encode_thumbs.py)、[播放代码](https://github.com/PC2005-cloud/dsh-pet/blob/main/dsh-pet/runtime/electron-helper/sprite.js)

**三、为什么观感有差距：基于本轮静帧的判断**

1. DeepSeek 的头发有较明确的发束亮部、暗部与局部遮挡，衣服有褶皱、蕾丝和层叠阴影；缩小后仍能读出体积。GPT 的白发白衣主要依靠紫色线条区分，浅部层次更接近，局部容易融成一片。
2. GPT 的轮廓与内部装饰线较醒目、密度较均匀，整体更偏平面插画。细节数量很多，视觉层级却未必更强。白色角色可以用冷暖、灰紫暗部和遮挡关系改善，而不必改成深色角色。
3. 两者头身比例与眼神不同，会直接影响第一眼气质。不能为追求 DeepSeek 的观感而擅自把用户选定长裙缩成二头身；应在既定比例内改善脸部焦点、色块与轮廓。
4. 小尺寸下眼睛、脸、发束和服装大关系应先读得清。母图只在放大图中精致，不足以保证桌面显示精致。

这些是美术判断，不是某种“画质分数”。当前首帧对照未完成整套 DeepSeek 动作的原速视觉审查，因此不对全部动作逐项评级。

**四、现有 GPT 制作里应该纠正的地方**

| 环节 | 已查到的 GPT 做法 | 对达到目标的影响 |
| --- | --- | --- |
| 母图风格 | 新待机提示词仍明确保持浅紫平涂与原画风 | 即使生成更稳定，也不会自行变成更有体积的上色方式 |
| 生成路线 | 已用本地 Wan2.2 与云端 Wan3.0；原作者公开确认的是豆包入口 | 路线可借鉴，生成模型的动画先验不能视为相同 |
| 源片缺陷 | 历史记录出现嘴形变化、半闭眼、线条变化；后续做跟踪局部修正 | 贴嘴或修眼解决局部问题，不能代替一段完整稳定的源片 |
| 透明边缘 | 自动颜色模型、轮廓引导与局部保护 | 可以改进，但与作者手工遮罩路线的工作量和控制程度不同 |
| 动作覆盖 | 历史版本包含姿态过渡动作；较新版本逐项换成连续视频 | 不应将动作数量、总帧数与精细程度混为一谈 |
| 播放 | GPT 使用 WPF 图集，DeepSeek 使用透明视频 | 应独立检查图集缩小、计时、缓存和切换；宿主差异本身不是画质不合格的证明 |

材料依据：`integrations/gpt-niang/animated/PIPELINE-AUDIT-20261021.md`、`IDLE-QUALITY-REWORK.md`、`PAUSE-20261021-THINKING.md`，以及 `work/gpt-niang-animation/video/wan3-idle-720-full-v1-motion-refined-v1/report.json`。这些历史制作记录的“通过”或用户当时接受某一待机，不代表目前整体目标已完成。

现有通用连续视频导入脚本仍有 24fps、最多256帧的约束，其他精修导入路径曾适配30fps。未来按实际选用入口核查，不能拿一个历史上限概括所有路径，也不能把30fps片段直接按24fps解释。

**五、复刻同等水平的具体做法（建议，尚未开始生成）**

1. **先确定静态目标。** 保留白发紫瞳、长裙比例、小嘴、角、翼、尾巴和结饰；旧母图保留。新增一版候选，重点改善白色区域的阴影、发束结构、线条粗细层次和小尺寸可读性。按可见高度200、300、400像素与 DeepSeek 同屏比较。用户未认可新的基础风格前，不展开动作库。
2. **先用一个待机验证生成路线。** 为同一张母图写一个8–10秒的低运动量单镜头：安静呼吸、一次自然眨眼、发梢和尾尖少量滞后运动、收回起始姿态。优先评估作者确认使用的豆包入口；已有Wan素材保留作对照。具体服务、模型版本和费用先核实，研究结论不构成开始新服务付费调用的授权。
3. **先审查未经修饰的源片。** 完整原速播放，逐帧查眼睛、嘴、手指、龙角、结饰和尾巴。人脸变形、饰品增生、服装结构变动反复发生时淘汰或重做源片。少量局部问题可跟踪修正；不把长期贴脸当作常规生产办法，不用插帧或放慢掩盖运动错误。
4. **完成接近手工级的透明处理。** 自动抠像先出初稿，再针对白发细丝、翼膜、袖口、手指间隙、裙摆和尾巴做局部遮罩、去溢色、颜色恢复与跨帧修整。可使用PR，或能达到同等边缘控制程度的其他工具；关键是结果，而不是软件名字。检查浅、深和鲜艳背景，避免以大幅收缩轮廓换取“干净”。
5. **统一构图，保存母版，再输出播放资源。** 整段共用尺度和地面基准，保留呼吸、跳跃与衣物运动。保存原始源片及高质量透明母版，桌面变体按目标可见尺寸与DPI制作。若源30fps则保留其节奏，不能为仿照DeepSeek的数字而静默删帧。中间画布扩大不等于超分辨率恢复细节。
6. **最后验证播放器和循环。** 在相同人物高度、同一背景中比较原速循环，查首尾跳变、脸部与衣纹闪烁、脚底漂移、边缘毛刺，以及等待新片时的闪黑。再查WPF实际呈现节奏、图集采样和切换停顿。只有证据显示现宿主造成无法接受的损失，才评估透明视频播放器；不预先重写整套程序。
7. **达到目标后逐个扩展。** 下一项可选托腮思考，其后再做点击回应与开心。每项都经过同一源片、抠像、原速播放和用户观感验收，先积累少量同水平动作。

建议第一个交付物只是：一张达到目标风格的母图 + 一段8–10秒待机 + 同高原速对比。样片的验收依据是用户是否觉得它与 DeepSeek 同样细致、自然，技术检查只负责排除损坏、裁切和掉帧。

**六、不能从公开资料确认的事项**

- 豆包所用具体底层模型版本、每段动作的实际参数/随机种子与重试次数。
- 原始母图的完整创作过程、全部人工挑选和修整工时、PR遮罩工程。
- 逐项达到同等观感所需的费用和工期。应在一个样片确定路线后估计，不能先承诺固定次数或“换同款模型即可完美”。

复用代码或素材链时保留原作者来源。作者README区分代码与素材的使用条件；后续若分发衍生作品，应按原项目说明处理。此次只完成研究和只读媒体检查。

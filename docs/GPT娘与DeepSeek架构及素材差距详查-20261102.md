# GPT娘与DeepSeek：当前架构、素材及后续影响

核查日期：2026-11-02。目标：以当前本机安装为依据，判断GPT娘要达到至少DeepSeek体验水平，哪些方面应保留、哪些方面应改造。

## 结论

两者当前底层路径不同。DeepSeek使用Electron/Chromium播放透明WebM；GPT娘使用PowerShell/WPF宿主、C#图集解码和逐帧选图。两者都有独立的窗口运动与点击反馈，不能把人物视频fps、程序更新频率、屏幕呈现频率合并为一个数。

明确的差距是：GPT的播放和资源管理更依赖自行维护；现有播放资源体积明显大；当前动作状态/校验上限不利于继续扩充；走路素材与窗口真实位移尚未像DeepSeek那样绑定；题材集中在姿态与情绪，生活和情景表演覆盖不足。

需要纠正此前判断：GPT并不是因为“384×384比640×360小”就必然不清晰。实际抽样人物高度，GPT安装帧约335像素，DeepSeek约266～267像素。当前GPT的分辨率不能被判定为已经低于DeepSeek；更明显的静态差别来自角色比例、色块与明暗层次，动态差别仍应检查源片和实际播放。

建议优先验证并改善播放稳定性、动作与窗口联动、素材的完整表演，之后决定是否更换渲染实现。保留高清母版、现有角色设定、WPF额度/状态功能及可回退安装，不再次把低清的Electron变体作为当然升级。

## 1. 本轮检查范围与当前状态

- 全量读取DeepSeek安装目录106个WebM的流信息、文件大小和SHA256；106个文件SHA不同，但不据此认定106个完全不同主事件。
- 核对GPT实际安装清单43状态、7500帧、125张图集；125张PNG的文件头尺寸与清单哈希全部一致。未将全量文件头读取冒称全帧解码或视觉审片。
- DeepSeek维护清单51项安装哈希一致。GPT初次对`0.7.3-physical-landing.1`包核对207项一致；随后另一会话更新了native-motion.cs、motion-selection.ps1、motion-runtime.ps1。最终再次读取的207项与`0.7.3-held-air-landing.1`清单全部一致，且已出现该包live-install.json安装回执。报告按该最终文件状态收尾，不把更新期间的三项差异当成损坏。
- 架构结论基于实际读取的文件；不把更新期间的旧基线差异当成损坏。本轮不修改或覆盖这些并行文件，不重启桌宠。
- 实际解码抽样：DeepSeek待机/张望首帧，GPT正面待机母版/现装首帧、已认可新版走路原片/现装首帧；统一可见人物高度300像素比较。另沿用本次聊天前一轮三段DeepSeek各120帧PTS核查。
- 未进行本轮全库艺术重审、鼠标注入、跨播放器同负载性能对照、屏幕逐帧捕获或GPU视频解码路径认证。画面最终验收仍由用户决定。
- Gemini六条新素材仍为原片保留状态，尚未安装；不能算进当前43状态。此前因60fps疑问停止的临时图集不作为正式素材。

## 2. 底层架构与后续影响

|方面|DeepSeek当前实现|GPT娘当前实现|后续影响与判断|
|---|---|---|---|
|宿主|Node/Electron，HTML/CSS/JavaScript|PowerShell/WPF，C#解码及原生运动辅助，Node状态观察|不同技术路线。WPF本身不等于低质量，Electron也不能自动保证更清晰、更省资源|
|人物播放|两个video元素交替，loadeddata和requestVideoFrameCallback等待目标画面就绪|异步读PNG图集，C#裁出帧，PowerShell按媒体时间更新Image.Source|GPT需自行处理预热、跨页、时钟、缓存、取消和收尾；长片、频繁切换增加维护压力|
|帧时钟|视频按自身时间戳播放，窗口运动另走requestAnimationFrame|约60Hz DispatcherTimer检查，正常动作按30fps索引变化选图|GPT存在UI线程负载影响选帧的路径；尚无本轮屏幕测量证明具体损失多少|
|透明与编码|VP9 WebM，106条均有alpha_mode标记|PNG RGBA图集，透明与颜色已烘焙进资源|PNG是无损存储，不能说编码天然比DeepSeek差；抠图错误和生成错误不会被无损保存修好|
|转场|双视频切换、180ms淡化|原生桥接路线、媒体帧归属判断及CPU像素Blend；一般180ms，拖动接点80ms|GPT对桥接和图集调度的维护更细。两者的淡化都不能替代缺失的真实收势|
|窗口运动|rAF、视频currentTime与漫游窗口位移联动，拖动/抛掷使用本地物理逻辑|C#原生运动，DwmFlush后台时钟；物理与动作通过状态/序号协调|GPT已有实质运动优化，不应说仍全靠低频PowerShell移动。维护记录还验证过66组抛掷轨迹；这不等于所有手感已完全相同|
|走路用途|startMoveDrive按视频时间控制起步停留、行进、刹车|现装walking为菜单视频表演，尚未找到以步态时间驱动窗口行走的实现|GPT新增再好的走路源片，仍可能是原地表演；需单独实现步态与位移同步，才有完整桌面行走体验|
|产品功能|桌宠聊天、自动长期记忆、本地语音、半身等定制|额度/任务状态观察、全半身、菜单和交互|功能目标不同。迁移播放不能顺手丢掉GPT现有状态功能，也不应默认必须复制聊天系统|

### 当前已经做过的优化，不应再按旧版批评

当前`Set-DragonCachedFrame`已取消每帧整图透明命中像素拷贝，按需读取；解码器已有锁与可复用的两个大数组；存在异步解码、冻结位图、裁片缓存、最多两个待加载请求、六页缓存、跨页提前请求及故障降级。窗口运动已采用DWM合成节奏，点击回弹另有WPF原生动画/Rendering处理。

因此，“GPT没有缓存、每帧都同步解码整张PNG、所有交互只有30Hz”均不符合当前代码。

### 仍需重点测量的路径

六页缓存淘汰/首次载入等路径可能调用`TrimMemory(false)`；该函数含强制完整GC与等待终结器。调用发生在合并加载结果的播放更新路径，存在停顿风险；本轮尚未通过性能跟踪把某次可见卡顿定位到它，不能直接宣称是唯一根因。

大页解码、按素材presentation参数做双线性重采样、跨动作CPU混合和UI调度，都是需要关注的成本。但DeepSeek的浏览器也有解码、进程与合成开销；不能用技术名称断言GPU一定加速透明VP9，或总内存必定更低。

## 3. 素材与资源实测

|指标|DeepSeek已安装|GPT娘已安装|如何解释|
|---|---:|---:|---|
|文件/动作口径|106个不同SHA的WebM文件|43个动作状态，含转姿/回姿/落地|不是同口径的独立表演数量，但GPT题材覆盖明显较窄|
|帧率|106条全为24fps|43状态全为30fps|GPT的源时序更密，不存在本机DeepSeek原片60、GPT原片30的差距|
|画布|全为640×360|每帧384×384|不能直接按画布面积判断人物清晰度|
|所抽首帧人物可见高度|待机267px、张望266px|正面待机335px、新版走路335px|GPT当前人物像素高度并不更低；该数据不是全库最低/最高值|
|GPT高清源样本|本轮未取得DeepSeek原始生成母版|782×1176画布，人物可见高度976px|GPT保留较高分辨率源，可重新输出；不等于976px每处都有真实同等级细节|
|安装播放资源大小|54,351,332字节，约51.83MiB|885,035,395字节，约844.04MiB|只统计WebM或图集，不含运行时。两边内容和帧数不同，不能当同片压缩率测试|
|源时长|WebM约4.92～10.04秒|7500帧合计250秒源时序|不把总时长直接当日常看到的内容丰富度|

当前384单元、8×8整页为3072×3072，32位像素展开为36MiB；六张整页约216MiB。这是像素缓冲的几何量，不是本轮测得的进程总内存，也不表示所有缓存页都是整页。另有解码缓冲、WPF对象和转场等开销。

高DPI与未来放大：GPT从976px可见高度缩到335px，确实舍弃了母版细节；若将来以超过335物理像素的角色高度显示，会再次放大有限像素。但抽样DeepSeek只有约267px可见高度，也存在放大上限。因此该问题应通过实际目标人物大小/DPI和母版重新输出解决，不能说“换640×360视频就会更高清”。

## 4. 素材画面质量：能确认什么

![同高首帧对照](../work/architecture-material-audit-20261102/same-height-first-frames.png)

每行左为DeepSeek已装首帧，中为GPT高清源，右为GPT安装图集首帧；全部统一可见高度300像素。第二行DeepSeek是张望，GPT是新版走路，作用是检查静态呈现，并非相同动作的动态对比。这里只观察首帧，不对两套全片做艺术通过/失败结论。

**静态上可观察的差别：**DeepSeek深蓝头发、亮部和深色衣裙形成较强分区，发束与服装遮挡关系比较突出；GPT白发白衣和密集细线更接近一个浅色整体，手、袖口、裙片之间容易依赖轮廓线区分。GPT长裙身体比例也让同高情况下的脸部占比小于DeepSeek，眉眼表情要更明确才容易在桌面上读出。这属于画风、比例与表演适配，不是改fps能解决的事。

**不能据此断言：**GPT整套线条都差、DeepSeek全套边缘都干净、当前GPU一定掉帧、角色只有换画风才有质量。已有GPT设定仍应保留，后续可在现有人设内调整主次明暗、关键动作剪影与表情幅度。

**动态质量证据尚缺：**本轮未完整观看106条DeepSeek和43状态全片；没有逐项重新评判手、嘴、尾巴、翼、边缘闪烁或脚底滑动。过去用户认可的片保持认可，Gemini说明中的“完美通过”也不自动当成本轮实测。真正差距应由用户在同高原速对照中判断，技术检查补充实际帧间隔、首帧延迟与卡顿位置。

## 5. 题材、连续性与扩展能力

GPT当前43状态中，turnfront/turnside两项转姿、proudarmsreturn和六条其他return共七项回姿、draglanding一项落地，共10项承担连接用途；余下33项也含待机与近似姿态，不能全部当成33种新剧情。

当前GPT自动日常池是proudarms、stretching、lookaround、sleeveside、wave、happy六项，其他题材不等于日常一定会随机看到。B节奏选择减少频繁连续表演，这是一项取舍：更安静，但主观上更容易觉得动作少。

DeepSeek文件题材覆盖吃东西、游戏、乐器、魔术、动物、季节节日、工作与点击回应；GPT现装集中在站姿、情绪、茶、扇、提灯等。用户认可的六条新原片能扩充读书、护宝、尾蝶、纸鹤、小翼和魔法故事，但当前尚未安装；不将派生图集或预览背景计为新增动作。

当前WPF校验限制：最多64个状态、单段最多600帧、只接受24/30fps、清单不超过128KiB，解码器仅接受320/384单元。43状态继续增至64后会被代码拒绝；30fps下600帧最多20秒。12秒原生30fps为360帧，目前时长规则可容纳；若以后支持60fps，12秒720帧还会同时触及帧数规则。它们是可修改的实现约束，不是WPF或电脑硬件的天然极限。

资源增长不会必然让所有图集常驻，因为缓存有上限；但更多复杂表演会增加安装/备份体积、冷加载、构建和维护成本。若单元边长翻倍，完整RGBA页像素体积约变四倍，不能只提高分辨率而不调整存储/解码路径。

## 6. 对后续质量的影响与优先级

|优先级|应解决的问题|继续不处理的影响|建议验证标准|
|---|---|---|---|
|P1|实际播放帧间隔、跨页/切片延迟、强制GC路径|源片更好也可能播放停顿；越复杂越难定位原因|相同素材/显示尺寸下，分别测稳定播放、跨页、切动作、冷加载；报告间隔分布和首帧延迟，不只报平均FPS|
|P1|走路和窗口位移、物理结束与动画衔接|好看的走路只能原地点播，落地可能与实际运动不同步|保留当前并行修复，单独核对步态支撑期、窗口轨迹、起停与中断；本轮不重改其规则|
|P1|更完整且有辨识度的源片表演|即使60fps也仍可能朴素、重复；道具无法形成故事|以用户认可为准，关键姿势、情绪转折、发袖裙尾跟随在实际尺寸下可读|
|P2|统一人物构图、尺度、原生收势与道具语义|容易出现大小跳变、双影、物体残留；新片接入成本增加|母版/参考/首末姿和用途登记清楚，实际接点原速对照；不把长淡化当真回姿|
|P2|适配目标尺寸的播放资源|放大时细节损失；盲目提高图集尺寸带来内存增幅|以人物物理像素高度而非画布宽度定规格，比较源和显示资源|
|P2|64状态及单段/清单限制|素材扩到DeepSeek量级之前便触及软件上限|建立明确资源索引与按需加载；回归加载失败/取消/恢复，不能仅放宽数字|
|P3|渲染器候选迁移|直接迁移可能再次模糊、重复实例、覆盖交互与设置|同素材、同人物大小、同DPI、同桌面进行A/B，改善成立再部署，保留回退与单一显示入口|

不建议将“全部补帧到60fps”作为当前首要工作：它不解决题材、身份稳定、接点或窗口联动；还会增加帧数和处理负担。若用户后续选定60fps，则区分原生与补帧、保留原片，并单独适配播放器，不能只改元数据。

建议长期方向是将视频解码/媒体呈现与行为调度、窗口物理、任务状态、资源构建发布分离。可以先在现有WPF内验证减少UI逐帧负担，也可比较独立的视频播放实现；不先把Electron当成唯一答案，更不共享改写DeepSeek的正式代码来试验。
